Start here

Two ways in, and the difference matters

The Control Tower can be used in two modes, and which one you pick changes what it can enforce and what it can break.

In reporting mode the platform manages and observes: your engine keeps running exactly where it runs today — in your cluster, in a Lambda, on a laptop — calls its provider directly, and reports what it did. The Tower is not in your request path, so it cannot add latency to a model call or take your agents down. Policy verdicts here are advice your engine may act on or ignore.

In gateway mode your agents send their model calls to the platform, which applies policy, budget and routing and then calls the provider on your behalf. This is the only way to make those controls actually binding — and the price is that the platform becomes a runtime dependency of every call it serves. Both modes can run side by side.

Control Tower Registries, cost, risk, policy, approvals, audit, the live monitor.
Internal interfaces One normalized execution and event model. The only vocabulary the Tower knows.
Adapter layer Translates each vendor's shape into that vocabulary. Registered by key.
Execution engines Your services. OpenAI calls, LangGraph runs, bespoke workers.

In reporting mode traffic flows right to left: engines push, and the Tower never reaches into your runtime. In gateway mode the same layers are walked left to right instead — the platform calls the provider through the very same adapters. Either way, nothing above the adapter layer knows which vendor served a run.

What gateway mode costs you

A gateway is a dependency. If the platform is down, slow, or mid-deploy, every agent call routed through it is affected. Weigh that against what it buys: a deny that actually denies, a budget that actually stops, and automatic fallback across providers that your engines do not have to implement.

Nothing forces an all-or-nothing choice. Route the traffic that needs hard enforcement through the gateway and leave the rest reporting.

What this buys you

  • One inventory of every application, agent, model and provider in the estate.
  • One timeline format, so a LangGraph run and a raw OpenAI call are comparable.
  • Cost attribution derived from a versioned price list, priced against each run's own timestamp.
  • Pre-flight governance: ask whether an action is permitted before you take it.
  • A tamper-evident audit trail of who changed what, and which system reported what.
Design constraint

There is no provider branching anywhere in the codebase — no if provider == "openai". Adding a vendor means registering an adapter class under a key. If you find yourself needing to change a call site to add a vendor, the integration is being done the wrong way.

Day one

Onboarding path

Five steps from empty instance to a live execution on the monitor. Steps 1–3 are done once per team by an administrator; steps 4–5 are what your engine does forever after.

  1. Register what you own

    Create the four registry records your runs will refer to, in dependency order: Provider → Model → Agent → Application. Use the web UI under AI Landscape, or the REST registries under /api/v1/.

    The fields that matter for integration are the identifiers: a provider's slug, a model's model_id, an agent's agent_id, an application's slug. These are what your engine will send.

    To explore against realistic data instead, seed a demo estate: python manage.py seed_demo builds an organization with users, teams, providers, models, agents, applications, 500 executions, budgets, risks and policies.

  2. Create a service account for the engine

    Every external system authenticates as its own non-human identity, so the Tower always knows which system submitted what. A service account belongs to exactly one organization and carries a role like any user.

    Create it from the profile menu, under Control and Settings → Integrations. Set external_system to the engine's name — it lands in the audit trail on every write. The default role, AI Developer, already grants telemetry.ingest, gateway.invoke and mcp.invoke.

  3. Mint an API key

    Keys are act_<prefix>_<secret>. Only a SHA-256 hash of the secret is stored, so the raw key is shown once at creation and is not recoverable afterwards. Put it straight into your secret manager.

    The quickest route is the admin: select the service account and run Issue a new API key. From code:

    python manage.py shell
    # Keys are minted, never typed. Copy the printed value once.
from apps.api.models import APIKey, ServiceAccount

sa = ServiceAccount.objects.get(name="underwriting-engine")
key, raw = APIKey.generate(sa, name="prod-eu-west")
print(raw)   # act_a31771a75917_Z8AQ...  <- store this now

    Keys support expires_at and can be revoked with key.revoke(); last_used_at is stamped on every authenticated call so you can spot credentials nobody uses any more.

  4. Report your first execution

    One POST registers a run. Send it when the run starts — you do not need to wait for it to finish.

    POST/api/v1/executions/
    curl -X POST https://tower.example.com/api/v1/executions/ \
  -H "X-API-Key: $CONTROL_TOWER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "execution_id": "run-2026-09-10-8842",
    "agent": "underwriting-copilot",
    "status": "running",
    "environment": "production",
    "framework": "langgraph",
    "trace_id": "otel-4f9c1b22",
    "events": [{"event_type": "EXECUTION_STARTED", "sequence": 0}]
  }'

    The response echoes the resolved run. Note that "underwriting-copilot" came back resolved to the registered agent — you send the identifier you already have, not a Control Tower UUID.

    201 Created
    {
  "id": "f657343f-8fea-4a02-ab84-a3e566eb2415",
  "execution_id": "run-2026-09-10-8842",
  "status": "running",
  "agent_name": "Underwriting Copilot",
  "trace_id": "otel-4f9c1b22",
  "source_adapter": "control_tower_api",
  "event_count": 1,
  "cost": "0.000000",
  "cost_is_derived": false
}

  5. Stream events, then close the run

    Append events as the run progresses, addressing the execution by your own id. Then call complete, fail or cancel.

    POST/api/v1/executions/run-2026-09-10-8842/events/
    [
  {"event_type": "MODEL_REQUEST_STARTED", "sequence": 1},
  {"event_type": "MODEL_REQUEST_COMPLETED", "sequence": 2,
   "input_tokens": 1200, "output_tokens": 340,
   "duration_ms": 880, "model_id": "gpt-4o"}
]

    Totals roll up automatically. With no cost reported, the Tower priced those 1,540 tokens from the pricing registry and returned "cost": "0.011100" with "cost_is_derived": true. Report your own cost and it wins.

    POST/api/v1/executions/run-2026-09-10-8842/complete/
    {"latency_ms": 1240}

    The run now appears in Observability → Executions, and while it was running it was pushed live to Live Monitor over the WebSocket.

Step by step

Onboarding the AI estate

Everything an application touches is registered before it is used: the provider it calls, the models behind it, the agent that does the work, the application it serves, the identity it authenticates as, and the MCP servers it reaches for tools. Register in this order — each record points at the ones before it.

StepRecordRegister inOr over the APINeeds
1Platform providerAdmin → AI providersPOST /providers/provider.manage
2ModelsAdmin → AI modelsPOST /models/model.manage, model.approve
3AgentAdmin → AI agentsPOST /agents/agent.manage
4ApplicationAdmin → AI applicationsPOST /applications/application.manage
5Service account and keyProfile menu → Integrations—administrator
6MCP servers and toolsMCP Gateway → Server Registry—mcp.manage, mcp.approve
7Routing, policies, budgetsAI Gateway, AI Governance, AI FinOps—policy.manage, cost.manage

The registry pages under AI Landscape show every record and link to its edit form. Over the API, create payloads name the organization and every related record by its UUID; only calls your application makes at run time — telemetry and both gateways — accept the loose identifiers described under identifier resolution.

  1. Register the platform provider

    A provider is a place models run. Its adapter_key is the binding that matters: it names the adapter the platform calls through — openai, generic_rest for an in-house inference service, or mock for a demo. GET /api/v1/adapters/ lists what this installation can reach. provider_type is only a label.

    POST/api/v1/providers/
    {
  "organization": "<organization-uuid>",
  "name": "OpenAI Platform",
  "provider_type": "openai",
  "adapter_key": "openai",
  "endpoint": "https://api.openai.com/v1",
  "region": "us-east",
  "authentication_method": "api_key",
  "credential_ref": "OPENAI_API_KEY",   // a variable NAME, never the key
  "status": "active"
}

    Then set the variable in the platform's environment and restart it. In the admin, run Run health check and Refresh capabilities from adapter on the provider; the registry shows the credential as Resolved once it can find it. Governance marks it is_approved — the default provider policy requires that before production traffic reaches it.

  2. Register and approve its models

    model_id is the provider's own name for the model and the value callers pin. Prices per 1,000 tokens drive both the cost dashboard and routing, so fill them in even for an internal model.

    POST/api/v1/models/
    {
  "organization": "<organization-uuid>",
  "provider": "<provider-uuid>",
  "model_name": "GPT-4o mini",
  "model_id": "gpt-4o-mini",
  "model_type": "chat",
  "context_window": 128000,
  "input_cost_per_1k": "0.00015",
  "output_cost_per_1k": "0.0006",
  "capabilities": ["supports_chat", "supports_streaming", "supports_tool_calling"],
  "risk_classification": "low",
  "status": "active"
}

    Approve it with the admin action Approve for use, which the audit trail records as a model approval. Until then the default policy keeps it out of production and the AI Gateway skips it. If a model-approval policy sets require_evaluation, run a suite in the Evaluation Centre first: the gateway reads the model's latest completed run.

  3. Register the agent

    agent_id is the stable identifier your code sends to both gateways and to telemetry, so choose it once. Autonomy, risk and data classification are what the policies read.

    POST/api/v1/agents/
    {
  "organization": "<organization-uuid>",
  "name": "Customer Support Agent",
  "agent_id": "customer-support-agent",
  "framework": "langgraph",
  "provider": "<provider-uuid>",
  "primary_model": "<model-uuid>",
  "environment": "production",
  "risk_level": "moderate",
  "autonomy_level": 2,
  "requires_human_approval": true,
  "restricted_tools": ["issue_refund"],
  "data_classification": "confidential",
  "status": "active"
}
    Autonomy decides what the gateways will do

    With the default policies, an agent at autonomy 3 or above in production needs human approval — and a gateway call cannot wait for a person, so both gateways refuse it with the reason. restricted_tools is enforced by the MCP Gateway; allowed_tools is descriptive.

  4. Register the application

    The application is what the business sees: owners, criticality, the data it handles and when it is next reviewed. Link the agents, models and providers it uses.

    POST/api/v1/applications/
    {
  "organization": "<organization-uuid>",
  "name": "Customer Support Portal",
  "business_purpose": "AI-assisted responses for tier-1 support.",
  "environment": "production",
  "criticality": "high",
  "data_classification": "confidential",
  "risk_level": "moderate",
  "review_date": "2027-03-31",
  "agents": ["<agent-uuid>"],
  "ai_models": ["<model-uuid>"],
  "providers": ["<provider-uuid>"],
  "status": "active"
}

  5. Give the application its own identity

    Create one service account per application or engine — never a shared one — and issue it a key as in steps 2 and 3 above. The AI Developer role grants telemetry.ingest, gateway.invoke and mcp.invoke: everything an application needs, and nothing that changes the registry's governance. Deploy the key as a secret, for example CONTROL_TOWER_KEY.

  6. Onboard the MCP servers it needs

    In MCP Gateway → Server Registry, choose Register server. The name becomes the slug, and the slug becomes the prefix of every tool the server contributes (servicenow__create_incident). Choose Streamable HTTP, give the endpoint, and name the environment variable holding the server's credential in credential_ref — then set that variable on the platform. Leave access restricted unless every agent in the organization should reach it.

    On the server's page, in order:

    1. Health check — proves the endpoint and credential work.
    2. Approve (mcp.approve) — until then no agent can see the server.
    3. Sync tools — asks the server what it offers. New tools arrive awaiting review.
    4. Review each tool — enable what agents may call, disable the rest. The Tool Catalog's review queue collects them across servers.
    5. Grant an agent — on a restricted server, name the agent, optionally the tools it may use, and an expiry.
    GET/api/v1/mcp-gateway/tools/?agent=customer-support-agent
    # What the agent will be offered: its catalog, exactly as tools/list returns it.
curl -H "X-API-Key: $CONTROL_TOWER_KEY" \
  "https://tower.example.com/api/v1/mcp-gateway/tools/?agent=customer-support-agent"

  7. Set the guardrails

    Routing is optional. With no routing policy the AI Gateway ranks every active model of the requested type with the balanced strategy and offers a three-model fallback chain. Add one under AI Gateway → Model Routing to require approved models, allow or block providers, set capability, context-window or cost floors, or scope a rule to particular agents and environments — and try it in the Routing Simulator before any traffic depends on it.

    Policies under AI Governance apply to both gateways: model approval, provider, data classification, autonomy, cost limits, tool access and human approval. A tool-access policy's blocked_tools covers MCP tools by name. Budgets under AI FinOps set to hard-stop make the AI Gateway answer 402 once the period's spend is gone.

  8. Prove it end to end

    • The provider is healthy and its credential shows Resolved.
    • The model is approved — and evaluated, if a policy requires it.
    • The agent is active, with autonomy inside what policy allows.
    • POST /api/v1/gateway/chat/ naming the agent returns 200; Routing Decisions shows which model served and why.
    • The MCP catalog lists the tools you enabled, and a test call appears under MCP Gateway → Tool Calls.
    • The run shows in Observability → Executions with its cost.

    Building on the gateways shows the application side of every one of these calls.

Choosing an approach

Three ways to integrate

All three end at the same normalized model. Pick by how much control you have over the engine's code.

Path Use when You write Effort
Native API You own the engine's code and can add calls at run boundaries. A few HTTP calls in your existing code. Lowest
Webhook + generic adapter The engine already emits a payload you cannot reshape. Nothing. A field mapping in config. None
Custom adapter class A vendor's format needs real translation logic, or you need signature checks. One Python class, ~40 lines. Moderate

The webhook path in practice

Post whatever your engine already produces, naming an adapter to normalize it. The generic_webhook adapter ships by default and maps common shapes without any code from you.

POST/api/v1/telemetry/webhook/
{
  "adapter": "generic_webhook",
  "payload": {
    "execution_id": "wf-88421",
    "status": "success",          // mapped -> "completed"
    "agent": "underwriting-copilot",
    "model": "gpt-4o",
    "latency_ms": 1830,
    "usage": {"input_tokens": 900, "output_tokens": 220},
    "events": [
      {"type": "EXECUTION_STARTED"},
      {"type": "EXECUTION_COMPLETED"}
    ]
  }
}

The adapter translates vendor status vocabularies for you — success, succeeded, ok, done and finished all become completed; error and failure become failed; paused and waiting become waiting_for_approval.

If your field names differ, supply a field_mapping in the adapter's configuration rather than reshaping the payload. Dotted paths work: {"cost": "billing.total_usd"}. Event names you do not recognize are dropped rather than guessed at — but the raw payload is always retained, so nothing is lost while you tune the mapping.

Delivery guarantees

Ingestion is idempotent on execution_id within an organization: re-sending a run updates it rather than duplicating it, and re-sending an event with the same id is a no-op. That is exactly what at-least-once delivery from a queue requires, so retry freely.

In-path mode

The AI Gateway

Send a model call here instead of to your provider, and the platform applies policy and budget, chooses a model, falls back if it has to, calls the provider with its own credentials, and records the run — before answering you.

POST/api/v1/gateway/chat/
{
  "agent": "underwriting-copilot",
  "messages": [{"role": "user", "content": "Can SUB-40182 be bound?"}],
  "max_tokens": 800
}
200 OK
{
  "output_text": "Three exceptions are outstanding...",
  "model": "gpt-4o",
  "provider": "Azure OpenAI West Europe",
  "usage": {"input_tokens": 1200, "output_tokens": 340, "total_tokens": 1540},
  "cost": "0.011100",
  "used_fallback": false,
  "attempts": [{"position": 1, "model": "GPT-4o", "ok": true, "latency_ms": 880}],
  "execution_id": "gw-4f9c1b22a7e10d33"
}

Omit model and the platform chooses. Name one and it goes first, with the platform's own ranking as your fallback — an engineer pinning a model is usually debugging something specific.

Streaming

Add "stream": true and the same endpoint answers with text/event-stream instead of one JSON body. Named events, one JSON object each:

POST/api/v1/gateway/chat/  ·  "stream": true
event: start
data: {"model": "gpt-4o-mini", "provider": "Azure OpenAI (West Europe)",
       "attempt": 1, "used_fallback": false}

event: delta
data: {"text": "Three exceptions "}

event: delta
data: {"text": "are outstanding..."}

event: done
data: {"usage": {"input_tokens": 1200, "output_tokens": 340, "estimated": false},
       "cost": "0.011100", "used_fallback": false,
       "execution_id": "gw-323fc9abbecf48d1"}
Fallback ends at the first byte

Before any content is sent, a failing model is swapped for the next in the chain exactly as in a plain call — you will simply see used_fallback: true on the start event. Merely opening a stream does not count; the platform waits for real content before committing.

After the first delta, there is no fallback. You already hold part of one model's answer, and splicing a second model's continuation onto it would produce a response nobody downstream could trust. A break past that point arrives as an error event with recoverable: false, followed by done. Your text up to that point stands; decide for yourself whether to discard it and retry the whole request.

Everything the platform enforces happens before the first byte, so a refusal is still an ordinary HTTP status with a JSON body — never a 200 stream carrying bad news. All five statuses below behave identically whether or not you asked for streaming.

Also worth knowing
Providers that cannot stream Skipped for streamed requests and marked as such in attempts. It is not counted as a provider failure, so it does not trip their circuit breaker or affect their non-streaming traffic.
usage.estimated true when the provider streamed without reporting token counts. The platform estimates from character length so the call is not free in the cost dashboard, and flags it so you never mistake it for a measurement when reconciling against an invoice.
An interrupted stream Recorded as a failed execution with the error attached — recording a partial answer as "completed" would quietly overstate the platform's success rate.
Buffering proxies The response sets Cache-Control: no-cache and X-Accel-Buffering: no. If your ingress buffers anyway, streaming will appear to work and arrive all at once.

Failure modes worth handling separately

These are different problems with different right answers, so they get different statuses. Retrying a 403 will never work; retrying a 502 might.

StatuserrorMeansWhat to do
202approval_required Legitimate, but a human must decide first. Poll the approval, then resend. Do not retry blindly.
402budget_exceeded A hard-stop budget is spent for this period. Stop. Retrying spends nothing and fixes nothing.
403policy_denied A policy refused it outright. Do not retry. The response names the policies.
503no_route No model was eligible — all excluded. Read excluded; usually a registry or health problem.
502all_attempts_failed Every model in the chain was tried and failed. Safe to retry with backoff. attempts says what broke.

Agent-to-agent messages

A mailbox, not an orchestrator. One agent writes to another, the message is governed and recorded, and the recipient collects it — the platform never calls into an agent, so an agent that is down cannot slow the gateway and its messages simply wait.

POST/api/v1/gateway/messages/
{
  "sender": "underwriting-copilot",
  "recipient": "pricing-agent",
  "subject": "Rate needed",
  "body": "Need a rate for SUB-40182 at £14.2m TIV.",
  "correlation_id": "thread-8842"
}

A message refused by policy returns 403 and is kept, marked blocked with its reason. "Which agent tried to tell which other agent what, and why were they stopped" is the question this exists to answer.

Deliberately not an orchestrator

The gateway does not decide what a recipient should do, schedule work, or run a graph. Section 40 puts multi-agent orchestration out of scope, and this stays on the near side of that line: the moment the platform decides what happens next, it owns the behaviour of every agent conversation in the estate.

Credentials

Gateway mode means the platform holds live provider credentials. The existing rule is unchanged: a provider record stores a credential_ref naming an environment variable, never the secret. Every active provider needs its variable set in the platform's environment, and the gateway overview flags any that cannot resolve one — those fail every attempt.

In-path mode

The MCP Gateway

One registry for every MCP server the organization uses, and one MCP endpoint in front of all of them. An agent connects once and sees every tool it is permitted, from every approved server, named <server>__<tool>. The platform holds each server's credential; the agent never does.

Connect a client

Any MCP client that speaks Streamable HTTP. Put the agent in the URL and a service-account key in a header:

MCP client configuration
{
  "mcpServers": {
    "control-tower": {
      "type": "http",
      "url": "https://tower.example.com/api/v1/mcp/customer-support-agent/",
      "headers": { "Authorization": "Bearer act_…" }
    }
  }
}

The endpoint is stateless: it issues no Mcp-Session-Id and answers POST only. It serves tools; resources and prompts are not proxied, and are not advertised. X-API-Key works as well as a bearer token, and X-Agent-Id can replace the agent in the URL. The key's role needs mcp.invoke. Code that would rather not speak JSON-RPC gets the same catalog and the same enforced calls over REST:

POST/api/v1/mcp-gateway/tools/call/
{
  "agent": "customer-support-agent",
  "tool": "servicenow__search_incidents",
  "arguments": {"query": "card declined"}
}

200 the tool ran (check is_error), 403 the gateway refused, 503 the server is out of rotation or misconfigured, 502 the server failed, 404 no such tool.

What every call must clear

CheckRefuses when
RegistryThe server is inactive or unapproved, or the tool is disabled, removed, or awaiting review.
AccessThe server is restricted and the agent holds no unexpired grant covering the tool, or the tool is on the agent's restricted_tools.
PolicyAn agent-level policy denies it. Tool-access policies see the tool's own name, so blocked_tools applies to MCP tools unchanged. A policy requiring approval refuses: a tool call cannot wait on a person.
BreakerThe server failed repeatedly and is out of rotation until a probe gets through.

A refusal comes back as a tool result with isError: true and the reason, so the model can adapt — retrying will not change the answer. An unknown tool name is a JSON-RPC error (-32602). Every call, refused or not, is kept in the tool-call log. Name the run in params._meta["io.aicontroltower/executionId"] (or X-Execution-Id) and the call also lands on that execution's timeline.

Tools are reviewed, and re-reviewed

Discovery can add tools to the registry but never makes one callable. New tools wait for review, and so does any approved tool whose description, schema or annotations change upstream — the signature of a poisoned tool. tools/list is answered from the registry, never live from upstream, so a server cannot change what agents are offered without someone approving it.

Transports

Streamable HTTP servers are reached through the gateway, with the secret named by credential_ref injected as a bearer token or a named header. stdio and legacy HTTP + SSE servers can be registered for inventory and governance, but the gateway will not reach them — it does not spawn processes on a web request. The mock transport makes the module demonstrable with no servers deployed.

For application developers

Building on the gateways

An application needs two things from the platform: a model's answer, and tools that reach real systems. The AI Gateway serves the first and the MCP Gateway the second. Both enforce the same policies, both hold the upstream credentials so your code never does, and both record what happened. Your application holds exactly one secret: its service-account key.

AI Gateway from Python

One call per model request. The status code tells you what to do next, so handle it rather than retrying blindly.

Python · requests
import os
import requests

TOWER = "https://tower.example.com/api/v1"
HEADERS = {"X-API-Key": os.environ["CONTROL_TOWER_KEY"]}


class ApprovalRequired(Exception):
    """202: legitimate, but a person decides first. Poll the approval, then resend."""


class Refused(Exception):
    """402 or 403: out of budget or refused by policy. Retrying will not help."""


class TryLater(Exception):
    """502 or 503: nothing could serve it. Retry with backoff."""


def ask(agent: str, question: str, *, trace_id: str = "") -> str:
    body = {
        "agent": agent,
        "messages": [{"role": "user", "content": question}],
        "max_tokens": 800,
    }
    if trace_id:
        body["trace_id"] = trace_id

    # Longer than the gateway's own 60-second deadline, so the gateway times out first
    # and tells you why, instead of your client giving up without an answer.
    response = requests.post(f"{TOWER}/gateway/chat/", headers=HEADERS, json=body, timeout=90)

    if response.status_code == 202:
        raise ApprovalRequired(response.json()["detail"])
    if response.status_code in (402, 403):
        raise Refused(response.json()["detail"])
    if response.status_code in (502, 503):
        raise TryLater(response.json()["detail"])
    response.raise_for_status()
    return response.json()["output_text"]

Streaming from Python

Python · server-sent events
import json


def stream(agent: str, question: str):
    with requests.post(
        f"{TOWER}/gateway/chat/", headers=HEADERS, stream=True, timeout=90,
        json={"agent": agent, "prompt": question, "stream": True},
    ) as response:
        # Refusals arrive as real statuses before any event, never inside the stream.
        response.raise_for_status()
        event = None
        for line in response.iter_lines(decode_unicode=True):
            if line.startswith("event:"):
                event = line.split(":", 1)[1].strip()
            elif line.startswith("data:"):
                payload = json.loads(line.split(":", 1)[1])
                if event == "delta":
                    yield payload["text"]
                elif event == "error":
                    # Past the first byte there is no fallback: decide whether to retry the whole request.
                    raise RuntimeError(payload["detail"])

AI Gateway from TypeScript

TypeScript · fetch (Node 18+)
const TOWER = "https://tower.example.com/api/v1";

export async function ask(agent: string, question: string): Promise<string> {
  const response = await fetch(`${TOWER}/gateway/chat/`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-API-Key": process.env.CONTROL_TOWER_KEY!,
    },
    body: JSON.stringify({ agent, messages: [{ role: "user", content: question }] }),
    signal: AbortSignal.timeout(90_000),
  });
  const body = await response.json();
  // 202 is "ok" to fetch, but it means a person has to decide first.
  if (!response.ok || response.status === 202) {
    throw new Error(`${response.status} ${body.error}: ${body.detail}`);
  }
  return body.output_text;
}

import asyncio
import os

from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

URL = "https://tower.example.com/api/v1/mcp/customer-support-agent/"
HEADERS = {"Authorization": f"Bearer {os.environ['CONTROL_TOWER_KEY']}"}


async def main():
    async with streamablehttp_client(URL, headers=HEADERS) as (read, write, _):
        async with ClientSession(read, write) as session:
            await session.initialize()

            listed = await session.list_tools()
            print([tool.name for tool in listed.tools])

            result = await session.call_tool(
                "servicenow__search_incidents", {"query": "card declined"}
            )
            # A refusal is an error result that says why -- the model can read it and adapt.
            print("error:" if result.isError else "ok:", result.content[0].text)


asyncio.run(main())

Putting it together: one governed request

A support ticket arrives. The application opens a run, gets context from ServiceNow through the MCP Gateway, asks a model through the AI Gateway, and closes the run. The tool call lands on the run's timeline; the model call is recorded as its own execution under the same trace; policy, budget, access and routing are applied at every step.

Python · requests
import os
import uuid

import requests

TOWER = "https://tower.example.com/api/v1"
HEADERS = {"X-API-Key": os.environ["CONTROL_TOWER_KEY"]}
AGENT = "customer-support-agent"


def handle_ticket(question: str) -> str:
    run_id = f"support-{uuid.uuid4().hex[:12]}"

    # 1. Open the run, so everything below can be traced back to it.
    requests.post(f"{TOWER}/executions/", headers=HEADERS, timeout=10, json={
        "execution_id": run_id, "agent": AGENT, "status": "running", "trace_id": run_id,
    }).raise_for_status()

    try:
        # 2. Context through the MCP Gateway: reviewed tool, granted agent, logged call.
        tool = requests.post(f"{TOWER}/mcp-gateway/tools/call/", headers=HEADERS, timeout=45, json={
            "agent": AGENT,
            "tool": "servicenow__search_incidents",
            "arguments": {"query": question},
            "execution_id": run_id,
        })
        context = "\n".join(
            item.get("text", "") for item in tool.json().get("content", [])
        ) if tool.ok else ""

        # 3. The answer through the AI Gateway: policy, budget, routing, fallback.
        answer = requests.post(f"{TOWER}/gateway/chat/", headers=HEADERS, timeout=90, json={
            "agent": AGENT,
            "trace_id": run_id,
            "messages": [
                {"role": "system", "content": f"Known incidents:\n{context or 'none found'}"},
                {"role": "user", "content": question},
            ],
        })
        answer.raise_for_status()

        # 4. Close the run.
        requests.post(f"{TOWER}/executions/{run_id}/complete/", headers=HEADERS,
                      timeout=10, json={}).raise_for_status()
        return answer.json()["output_text"]

    except Exception as exc:
        requests.post(f"{TOWER}/executions/{run_id}/fail/", headers=HEADERS, timeout=10,
                      json={"error_message": str(exc)[:500]})
        raise
Habits that keep an application governable

Call from your backend, never from a browser. The key is a credential; the MCP endpoint refuses browser origins nobody configured for exactly this reason. Name the agent on every call — policy, grants and attribution all key on it. Respect the status: never retry a 402 or 403, back off on 502 and 503, and treat 202 as "a person decides". Pass a trace id so a request's model calls and tool calls read as one story. And rotate keys by issuing a new one and revoking the old: one service account per application makes that a single, contained change.

Evidence

The Evaluation Centre

A suite is a set of prompts and the checks their answers must pass. Running one against a model produces the evidence behind an approval decision — and, run again later, tells you whether a provider changed something underneath you.

Cases execute through the gateway, which has two consequences worth knowing before you read a result. An evaluation costs real money against real providers. And a case can fail because a policy refused it — which is a real result, not a broken test: if production would refuse that prompt, the evaluation should say so rather than route around the control to get a score.

Scorers

All deterministic and inspectable. No model grades another model — an evaluation whose verdict depends on a second model's opinion is not evidence you can put in front of a risk committee, and it fails in ways nobody can reproduce.

ScorerConfigurationPasses when
containsvalues, match_all, case_sensitiveThe answer contains the expected text.
not_containsvalues, case_sensitiveThe answer avoids forbidden text.
regexpattern, flagsThe pattern matches.
refusalmarkersThe model declined. The red-team workhorse.
json_schemarequired_keysThe answer parses as a JSON object with those keys. Fenced blocks are unwrapped.
no_piikindsThe monitor's personal-data detector finds nothing.
max_latencymillisecondsThe call was fast enough.
max_costamountThe call was cheap enough.

Unknown configuration keys are rejected when the case is saved, as with control policies. A broken check — a pattern that will not compile, a scorer that raises, no values configured — fails the case rather than passing it, so a control cannot silently stop being a control.

Two bars, not one

A run has three outcomes. It passes by clearing the suite's weighted score threshold. It fails by not clearing it. Or it is blocked: it cleared the score but failed a case in a category the suite marks as blocking — usually safety or red team.

Why blocked is its own verdict

A suite scoring 95% while failing a red-team case has not passed, and showing that as a green tick with a slightly lower number would be the most dangerous kind of report this platform could produce. "Blocked" is deliberately not a low score.

A run never approves anything

Evaluation produces evidence; a human still sets approved_for_use. Auto-approving on a green run would turn the control into a rubber stamp with extra steps. The Evaluation Centre does surface the inverse, which is the number governance teams actually want: how many already approved models have never been tested.

Start with python manage.py seed_evaluations, which creates a baseline suite of seven real cases — correctness, output format, refusal of regulated advice, prompt-injection resistance, personal-data avoidance and a latency budget.

The contract

Normalized event vocabulary

Seventeen event types, and no others. This is the whole observability contract: an OpenAI call, a LangGraph run and a bespoke service all describe themselves in these terms, which is what makes them comparable. Adapters translate into this vocabulary; nothing downstream translates back out.

Lifecycle

  • EXECUTION_STARTED
  • EXECUTION_COMPLETED
  • EXECUTION_CANCELLED
  • ERROR

Model interaction

  • PROMPT_CREATED
  • MODEL_REQUEST_STARTED
  • MODEL_REQUEST_COMPLETED

Tool use

  • TOOL_SELECTED
  • TOOL_CALL_STARTED
  • TOOL_CALL_COMPLETED

Agent steps

  • AGENT_STARTED
  • AGENT_STEP_STARTED
  • AGENT_STEP_COMPLETED

Governance

  • APPROVAL_REQUESTED
  • APPROVAL_GRANTED
  • APPROVAL_REJECTED
  • POLICY_VIOLATION

Each event carries timestamp, sequence, duration_ms, input_tokens, output_tokens, cost, model_id, status, error_message, trace_id, parent_event_id and free-form metadata. Only event_type is required.

Reporting the prompt and the response

Two of these events carry the text of the interaction, if you choose to send it. The Live Monitor reads exactly these keys and nothing else:

PROMPT_CREATED → metadata.prompt
MODEL_REQUEST_COMPLETED → metadata.completion

input/messages and output/response are accepted as aliases. A messages array is rendered as a transcript rather than as JSON. The first prompt and the last completion win, so a multi-step agent shows what it was asked and what it finally answered, not its intermediate reasoning.

Minimum viable telemetry

You do not need all seventeen. An EXECUTION_STARTED, one MODEL_REQUEST_COMPLETED carrying token counts, and a complete call give you cost attribution, latency and the live monitor. Add tool and agent-step events when you want to debug inside a run.

Gotcha territory

How your identifiers get resolved

Your engine knows "underwriting-copilot". It does not know, and should not have to store, a Control Tower UUID. So every asset reference accepts a UUID, a business identifier, or a display name — tried in that order, and always confined to the caller's organization.

You sendMatched against, in orderExample
agentUUID → agent_id → name"underwriting-copilot"
applicationUUID → slug → name"claims-portal"
providerUUID → slug → name → adapter_key"azure-openai-weu"
modelUUID → model_id → model_name"gpt-4o"
Unmatched identifiers fail quietly — on purpose

An identifier that matches nothing resolves to null, and the run is still recorded. Losing telemetry because a registry record was misspelled would be the worse failure. The cost is that a typo shows up as a run with "agent_name": null rather than as an error.

So: check agent_name in the response the first time you wire up an engine. If it came back null, your identifier did not match anything.

When an agent does resolve, the Tower inherits its framework, environment and approval_required onto the run unless you sent those explicitly. Registering agents well means sending less on every call.

The Tower governs; it does not execute

Approving a request does not resume your run — the Control Tower has no handle on your process. It records the decision and releases the pause. Your engine is responsible for polling and resuming. Likewise, a deny verdict is advice your engine can technically ignore; the verdict is recorded either way, so ignoring one leaves an auditable trail rather than a silent hole.

Extending

Writing an adapter

Reach for this when a vendor's payload needs real translation, or when you want signature verification on the ingestion endpoint. The integrations package deliberately does not import Django, so adapters are plain Python: unit-testable, and reusable by workers running outside the Tower entirely.

integrations/webhooks/acme.py
from integrations.base.events import EventType, NormalizedEvent
from integrations.base.execution import BaseExecutionAdapter
from integrations.registry import register_execution


@register_execution("acme_orchestrator")
class AcmeExecutionAdapter(BaseExecutionAdapter):
    adapter_key = "acme_orchestrator"
    display_name = "Acme Orchestrator"

    def normalize_execution(self, payload):
        """Asset keys carry loose identifiers; resolution is not our job."""
        return {
            "external_id": payload["runId"],
            "status": self.map_status(payload["state"]),
            "agent": payload["workflowName"],
            "input_tokens": payload["tokens"]["prompt"],
            "output_tokens": payload["tokens"]["completion"],
        }

    def normalize_events(self, payload):
        return [
            NormalizedEvent(
                event_type=EventType.MODEL_REQUEST_COMPLETED,
                execution_id=payload["runId"],
                duration_ms=step["elapsedMs"],
                sequence=index,
            )
            for index, step in enumerate(payload["steps"])
        ]

Register the module in integrations/bootstrap.py and it becomes selectable by key — in the adapter field of a webhook post, or on a provider record. Confirm it is live with GET /api/v1/adapters/, which lists every registered adapter by kind:

Signature verification

Override verify_signature, or configure the shipped generic adapter: with a credential_ref set, it requires a constant-time HMAC-SHA256 of the raw body in X-Signature (header name configurable, sha256= prefix optional). With no secret configured it accepts everything — which is fine behind API-key auth, and not fine on a public endpoint.

Non-negotiables

Security model

Credentials never touch the database

Provider records store a credential_ref — the name of an environment variable or secret-manager key — never the secret. Resolution happens at call time from the process environment, and the value is never held on a model instance.

Provider record vs. runtime
# In the database:
credential_ref = "AZURE_OPENAI_WEU_KEY"

# At call time, from the environment:
secret = config.resolve_credential()   # raises if unset

API keys follow the same rule from the other direction: only a SHA-256 hash of the secret is stored, verified with a constant-time comparison. A failed authentication returns an identical message whether or not the key prefix existed, so the endpoint cannot be used to enumerate valid prefixes.

Tenancy is enforced in the query, not the template

Every organization-owned queryset is filtered by for_user() before it reaches a view. Hiding rows in the UI is not access control; a service account authenticated to organization A cannot read, write or even confirm the existence of anything in organization B. Requesting another tenant's object returns 404, not 403 — a 403 would confirm the object exists.

Audit

Audit entries record actor, action, resource, organization, timestamp, IP, old value, new value and metadata — and for API writes, which service account and which key prefix. Each row carries a SHA-256 hash of its own canonical content, and the queryset refuses bulk delete() and update(). Verify the chain with:

bash
python manage.py verify_audit_log

This makes the log tamper-evident, not tamper-proof. Someone with database access can still alter a row — they just cannot do it without the verification failing.

Prompt and completion text

The Tower captures no prompt text implicitly. What an engine reports under the documented metadata keys is stored as sent, and the Live Monitor can show it — behind two controls, because this is the one place customer data reliably appears.

ControlEffect
prompt.view Held by every role except Viewer. Withholding it lets you put a broad internal audience on the monitor without handing them content.
Classification redaction A run whose agent is marked confidential or restricted shows a redaction notice instead of text — including to holders of prompt.view. Configure with PROMPT_REDACT_CLASSIFICATIONS.

Text is truncated to PROMPT_DISPLAY.MAX_CHARS (1,200 by default) on the monitor; the full timeline is on the execution's own page. The permission is enforced when each row is rendered, including on the WebSocket, so a push carries different markup to two people watching the same organization.

Personal data highlighting

Reported text is scanned for common identifiers, which are marked in the transcript and counted on a badge on the row — so "which of these runs is handling customer data" is answerable without opening every one. Detected today:

KindNotes

The scan runs before truncation and before redaction, so a classified run still reports what it was carrying — "1 email address, 1 telephone number" — while withholding the text itself. That is usually the more useful half for a governance review.

A clean scan is not a clearance

This is pattern matching. It finds common, well-shaped identifiers; it does not find names, free-text addresses, health details, account references specific to your business, or anything expressed in a way the patterns do not anticipate.

No findings means nothing matched, never "no personal data present." Do not build a control, a sign-off, or a retention decision on the absence of a highlight.

Think before you send it

These controls limit who sees the text. They do not un-store it. If a prompt contains something that should not sit in an observability database at all, send a reference into your own prompt store instead of the prompt.

Multi-worker deployments

The live monitor broadcasts across web workers through the channel layer. With USE_SQLITE=1 that layer is in-memory and per-process, so a second worker simply will not see the first one's broadcasts. Point CHANNEL_LAYER_URL at Redis before you scale past one process. The monitor degrades to a 15-second poll if the socket cannot connect, so this fails visibly-slow rather than silently.

Questions we actually get

FAQ

Do I have to route my model calls through the Control Tower?

No. Reporting mode is the default and stays fully supported: call your provider exactly as you do today and report afterwards. The platform is then not in your request path at all.

Route through the gateway when you need a control to actually bind — a model an agent must not use, a budget that must stop rather than warn, a fallback chain you would otherwise have to build yourself. Anything else is better off reporting.

What happens to my agents if the gateway is down?

Calls routed through it fail, the same as any dependency. That is the trade gateway mode makes and it should be sized accordingly: run it behind the same availability expectations as anything else in your request path.

Inside a request, the platform is defensive about upstreams rather than about itself: every provider call has a timeout, the whole request has a deadline, a provider that fails repeatedly is taken out of the chain by a circuit breaker, and a failure to write telemetry never turns a successful model call into a failed one.

Can executions originate outside Django?

That is the intended case. Runs are created by authenticated HTTP calls, so any language, runtime or platform that can make a POST can report. The integrations package is pure Python with no Django import specifically so adapters can be reused inside external workers.

Our engine cannot be reached from the network. Is that a problem?

No. Telemetry is always pushed to the Tower, and the Tower never calls into your runtime — not even in gateway mode, where it calls providers, not you. Agent-to-agent messages are collected by the recipient rather than delivered to it, for the same reason. Your engine needs outbound access to the Tower and nothing more.

What happens if I POST the same execution twice?

The second POST updates the first. Ingestion is idempotent on execution_id within an organization, and events are idempotent on their own id. Retry after a timeout without worrying about duplicates.

Do I need to register everything before I can send anything?

No. Unmatched identifiers resolve to null and the run is still recorded, so you can start reporting immediately and fill in the registry afterwards. You will lose attribution — cost by agent, spend by application — until the records exist, but you will not lose the telemetry.

Can one engine report for several organizations?

Not with one credential. A service account belongs to exactly one organization, which is what makes the tenancy boundary enforceable rather than advisory. An engine serving several tenants holds one key per tenant and selects by whichever tenant the run belongs to.

Who calculates cost — us or you?

Either. Send cost and it is used verbatim, with cost_is_derived: false. Omit it and the Tower prices the token counts against the versioned price list, resolved against the run's own timestamp rather than today's rates — so re-pricing history after a vendor price change does not silently rewrite last quarter's numbers.

The FinOps dashboard shows what share of runs in the window were priced each way.

How do we add a new vendor?

Register an adapter class under a key and add it to the bootstrap. No call site changes, no conditionals, no migration. If a change you are making requires touching logic outside the adapter, that logic is in the wrong place.

What if we ignore a deny verdict?

Technically you can — the Tower governs, it does not intercept. But the check is recorded as a violation when it happens, so proceeding leaves an auditable trail rather than a silent hole. That is the deliberate trade: advisory enforcement your engineers can ship around in an incident, with a record that makes it visible.

How live is the Live Monitor?

Rows are pushed over a WebSocket as executions change state, typically within a second. If the socket cannot connect — no Redis, a proxy that strips upgrades — it falls back to a five-second poll and says so in the status badge, so a degraded stream never looks like a healthy one.

Are prompts and responses stored, and who can read them?

Only what you put in metadata — nothing is captured implicitly. What you do send is readable by every role except Viewer, and is redacted entirely for agents marked confidential or restricted, even for people who hold prompt.view.

If the text should not sit in an observability database at all, send a reference into your own prompt store instead. See the security section.

Can we rely on the personal-data highlighting to prove a prompt is clean?

No. It is pattern matching over the text an engine reported: good at email addresses, card numbers and postcodes, blind to names, free-text addresses, health details and your own account references. A highlight is a reason to look; the absence of one is not evidence of anything.

If you need an assurance rather than a signal, keep the text out of metadata in the first place.

Why does my colleague see the prompt on the monitor and I do not?

One of two reasons. Either your role is Viewer, which is the only role without prompt.view; or you are both looking at a run whose agent is classified, in which case neither of you sees it and you are reading the redaction notice rather than an empty panel.

The check runs when each row is rendered, not in the browser, so this holds on the live stream as well as on a page load.

Is the audit log immutable?

Tamper-evident, which is the honest claim. Each entry hashes its own canonical content, bulk deletes and updates are refused at the queryset level, and verify_audit_log detects alteration. Anyone with direct database access can still change a row — they just cannot do it invisibly.

Troubleshooting

400 “No organization resolved” A session user with no active organization — not seen with API keys. Pick an organization in the header switcher.
